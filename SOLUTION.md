# Описание решения

## Данные и защита от утечки

Корпус поиска — исходные 189 212 объявлений `benchmark_items.parquet`.
Предсказания строятся для 2 452 запросов `benchmark_queries.parquet`.
История взаимодействий используется для географических вероятностей и
частот текста. Для локальных rtrain/val/test это 454 043 строки `hist`,
для benchmark разрешён полный train из 497 673 строк. В поставке сохранены
только используемые колонки train/hist, с исходным порядком и всеми строками.

Ранкер обучен на rtrain: 5 334 запросах и соответствующих релевантных парах.
Все найденные кандидаты, кроме релевантных, используются как отрицательные
примеры. Разметка val/test используется только в модуле проверки качества.
В модель не передаются query_id, item_id, число релевантных объявлений,
популярность релевантных объявлений из разметки или готовый ответ.

## Поиск кандидатов

1. **BM25 + география**, 1 000 кандидатов: title дважды, параметры[:600],
   description[:1500]; lowercase, ё→е, токены букв/цифр, русский Snowball.
   BM25 k1=1.2, b=0.75, географический вес 2.0.
2. **BM25F + география**, первые 350 кандидатов: раздельные поля title,
   вид/тип услуги и названия прайс-листа, description[:4000], прочие параметры,
   адрес. Веса title=2, остальные=1; b(title)=0.9, остальные=0.75,
   k1=1.2, географический вес 1.5. Нормированные частоты полей складываются
   до BM25 saturation.
3. **multilingual-e5-base + география**, первые 350 кандидатов:
   cosine + 0.005·log P(item_location|search_location). Веса не дообучались.
4. **e5 без географии**, первые 350 кандидатов: семантические ответы за
   пределами основной локации, включая удалённые услуги.

У e5 объявления кодируются как заголовок + выделенные regex названия услуг
+ первые 300 символов описания; запрос — текст + текст фильтров.
Префиксы `passage: ` / `query: `; лимит 512 токенов, нормированные fp16
embeddings. Точная версия модели записана в `release.json`.
Опубликованные плотные каналы содержат 2 000 / 500 кандидатов, лексический
BM25F — 2 000. Ранкер читает полные каналы для признаков score/rank, но
для попадания в объединение действуют квоты выше.

При объединении удаляются повторы пары (query_id,item_id). Если кандидатов
больше 2 000, применяется RRF с константой 60 и порядком item_id при равенстве.
Средний размер val-пула — около 1 477 кандидатов; полная полнота 0.9865.
Таблицы поиска являются сохранёнными результатами вычислений, а не ручной
разметкой. Они зафиксированы вместе с embeddings для побитового воспроизведения
GPU-расчётов на CPU у проверяющего.

## 58 признаков пары и LightGBM

- score, rank и разность с лучшим score запроса у каждого из четырёх каналов;
- покрытие слов запроса в заголовке, параметрах, типах и услугах прайс-листа;
- Jaccard для заголовка, точная фраза, покрытие текста фильтров;
- совпадение города, эмпирический log geo, расстояние по координатам;
- сглаженный geo с распределением по городам и поправкой на плотность корпуса;
- rating, log числа отзывов, log цены, категория и микрокатегория;
- длины текстов, скрытый телефон, запрет сообщений;
- наличие/число фильтров и совпадение Вид/Тип/Тип автосервиса;
- прайс-лист, опыт, оказание услуг онлайн/у себя/с выездом;
- длина запроса, наличие фильтра, частота текста в разрешённой истории, тип локации;
- e5 cosine для любой пары в объединённом пуле.

Используются три LightGBM binary-модели, seeds 17/23/42, по 200 деревьев.
Параметры: learning_rate=.055, num_leaves=31, min_data_in_leaf=90,
feature_fraction=.9, bagging_fraction=.9, bagging_freq=1, max_bin=127,
lambda_l2=5, num_threads=3. Все отрицательные примеры пула включены в обучение.
Каждая положительная пара имеет вес 60/n_rel данного запроса, отрицательная — 1.
Пропуски превращаются в -999; бесконечности — в ±999.
Три вероятности усредняются в float32. Пары сортируются по score убыванию,
затем item_id возрастанию. Возвращаются ровно 50 уникальных item_id на запрос.

## Проверка качества

Валидация выполняется в реальном benchmark-корпусе. val/test по 2 000 запросов,
по одному запросу на уникальный текст, с исключением релевантных item из hist
и разделением наборов по item. Распределения локаций, фильтров, частоты и длины
текста приближены к benchmark. Подробности — `provenance/VALIDATION.md`.

Итог: val Recall@50=0.9400, test=0.9276. Улучшение против BM25-анкера на val
+0.0810 с парным 95% CI [+0.0678,+0.0938]. Выбор варианта сделан на val,
test использован для подтверждения release candidate.
Числа test относятся к локальному отложенному набору, а не тестам платформы.

В поставке `run.py verify` заново считает benchmark/val/test ответы,
проверяет идентичность SHA-256 и локальные метрики через исходный harness.
Эталонные ответы не используются при расчёте признаков или инференсе.

## Анализ ошибок и ограничения

У val 0.0135 потери полноты связано с отсутствием нужного объявления в пуле,
ещё 0.0465 — с позицией ниже 50 внутри пула. Наиболее слабые сегменты:
широкий поиск по России 0.8154, широкая Москва 0.8491, однословные запросы
0.8176, релевантные объявления без отзывов 0.8571. Dense-канал помогает
семантическим несовпадениям, отдельные поля BM25F уменьшают влияние шаблонов
и адресов, geo и фильтры уточняют короткие запросы.

В локальных экспериментах ранкер с binary objective оказался лучше LambdaRank;
использование всех отрицательных примеров улучшило качество относительно
сэмплирования. Исторический дополнительный канал дал лишь +0.0010 полноты
пула и в эту версию не включён. USER-bge-m3 был исследован отдельно, но
поставленный четырёхканальный ранкер не использует его. Fine-tuning энкодера
в этой версии не проводился.

Поставка зафиксирована на данном наборе входов и промежуточных артефактов.
Для нового корпуса или иных запросов требуется заново построить retrieval и
embeddings по исходникам из `provenance/`. Повторное GPU-кодирование может
менять fp16-округление, поэтому для воспроизведения файла поставляются
именно исходные численные артефакты. Локальная валидация может быть оптимистичнее
платформы из-за плотности похожих объявлений и устройства benchmark.
